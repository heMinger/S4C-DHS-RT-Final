## 问题 1：深度坐标是否一致（Z-depth vs ray distance）

**结论：不一致，确认存在单位/坐标不匹配。** 代码把 DA3 的 Z 深度直接当成"光线距离"使用，缺少 `t* = d* / v_z` 转换。

### 证据链

1. 射线方向是**单位向量**：
   - `models/common/util/util.py:244 gen_rays()`，`norm_dir=True`（默认）
   - `models/common/util/util.py` 中 `unproj_map()`：`if norm_dir: unproj /= torch.norm(unproj)` → 归一化
   - `cam_raydir = R @ cam_unproj_map`，旋转矩阵保范数 → **v 是单位向量**

2. 因此 `xyz = ray_o + z_samp × ray_d` 里的 `z_samp` 是**光线距离 t**（沿单位射线的欧氏距离），不是 Z 深度：
   - `ARCHITECTURE.md:136`：`xyz = ray_origin + z_samp × ray_direction`

3. 渲染深度也是光线距离：
   - `models/common/render/nerf.py:417`：`depth_final = torch.sum(weights * z_samp, -1)`

4. 代码自己承认"光线距离 ≠ Z 深度"，专门写了转换函数：
   - `utils/projection_operations.py:27 distance_to_z()`，第 40 行 `factors = cam_points[...,2] / torch.norm(cam_points)`，第 42 行 `return depths * factors` → 即 `z_depth = ray_distance × v_z`
   - 用于把渲染深度转成 Z 深度去跟 LiDAR GT 比较：`models/bts/evaluator.py:116-117`、`evaluator_lidar.py:289`、`trainer.py:431-432`

5. DA3 深度是 **Z 深度**（metric 单目深度，沿光轴），且**未做任何转换**：
   - `datasets/kitti_360/kitti_360_dataset.py:791`：`depth_uint16 = depth_meters × depth_da3_scale`
   - `:825-826`：`depth = depth / self.depth_da3_scale`（uint16/256 → 米）
   - DA3 的 metric 分支输出 Z 深度，`docs/DA3在KITTI360上的表现与设置分析.md` 用 `median_ratio = gt_lidar / pred_depth` 直接对标 LiDAR Z 深度（无 v_z 修正）→ 证明 DA3 = Z 深度

6. 关键：`sample_adaptive` 和 `occlusion_supervision_loss` 都把 DA3 Z 深度直接与 `z_samps`（光线距离）比较：
   - `models/common/render/nerf.py:175-190`：`da3_depths = da3_depths.clamp(near, far)`、`sigma = absrel × da3_depths`、`d_min = da3_depths − 2σ`（把 Z 深度当光线距离做采样中心）
   - `models/bts/model/loss.py:74-76`：`free_mask = z_samps < d − margin`、`surf_mask = |z_samps − d| ≤ band`（Z 深度 vs 光线距离直接相减）

### 后果

- 离轴（侧视/图像边缘）射线 `v_z = cos(θ) < 1`，真实表面在 `t* = d*/v_z > d*` 处。
- 采样：表面窗口 `[d*−2σ, d*+2σ]` 被放在光线距离 `d*` 处，实际表面更远 → 离轴射线系统性**采样偏近**、错过表面。
- A5 loss：surf band 放在错误（偏近）位置，且 `[d*, d*/v_z]` 这段**真实自由空间被归进 "behind" 掩码而不被监督**。
- 误差随离光轴角度增大，最坏在侧视区域 → 与 `seg_acc_side`（0.43~0.47）远差于 `seg_acc_front`（0.74~0.77）的现象一致。

## 问题 2：A5 是否监督了最终密度（是否经过 Ray Transformer）

**结论：部分成立，存在训练/评估不一致。** 损失梯度**能**反向传播到最终密度 σ（经过 RaySigmaCorrector），但最终 SSC 评估读取的 σ 路径与训练不完全一致。

### "Ray Transformer" 是什么

- 代码里没有叫 "transformer" 的类；对应组件是 **`RaySigmaCorrector`**（基于坐标编码的 ray self-attention）：
  - `models/bts/model/models_bts.py:19 class RaySigmaCorrector`，`:35 nn.MultiheadAttention`
  - 配置开启：`configs/exp_kitti_360.yaml:71 ray_attention: enabled: true`

### sigma 数据流（关键）

```
raw_sigma = MLP(xyz)
raw_sigma += RaySigmaCorrector(coord_enc, ray_K)   # 仅当 ray_K 传入
sigma = relu/softplus(raw_sigma)
alpha = 1 - exp(-sigma × dt)
weights = T × alpha                                # ← A5 loss 用这个
```

- `models/bts/model/models_bts.py:408-416`：`raw_sigma = mlp_output[...,:1]` → `raw_sigma += sigma_correction`

### A5 损失用的是什么权重

- `models/bts/trainer.py:386-387`：`coarse_w = render_dict["coarse"]["weights"]`、`coarse_z = render_dict["coarse"]["z_samps"]`
- 这些 weights 来自**校正后**的 sigma（渲染路径 `nerf.py:365 model(pnts, ray_K=K)` 传了 ray_K）。

**所以：A5 损失确实"经过"了 Ray Transformer，梯度会回传到 RaySigmaCorrector 和 MLP → 最终密度。不是"加在 RT 之前"而绕过它。**

### 但存在 train/eval 不一致（重点）

| 路径 | ray_K | RaySigmaCorrector |
|------|-------|-------------------|
| 训练渲染 | `nerf.py:365` 传 `ray_K=K`（真实射线采样数） | ✅ 生效，沿真实射线方向 |
| SSCBench 评估 | `evaluate_model_sscbench.py:699 PSEUDO_RAY_K=64`，把 X 轴体素 64 个一组当"伪射线"传 `ray_K=64` | ⚠️ 生效，但**方向是 X 轴，不是真实射线方向** |
| evaluator_occ.py | `:436 net(q_pts, only_density=True)`，**不传 ray_K** | ❌ 完全不生效（用未校正 sigma） |

证据：
- `scripts/benchmarks/sscbench/evaluate_model_sscbench.py:712-719`：`use_pseudo_rays = (ray_attention_enabled and PSEUDO_RAY_K is not None)`；`:724 K = PSEUDO_RAY_K`
- `models/bts/evaluator_occ.py:436`：`self.renderer.net(q_pts_.unsqueeze(0), only_density=True)`

### 含义

- A5 只约束"训练时用于渲染的、校正后的 σ 权重"。
- 但最终 3D 指标读取的 σ 是**另一条路径**：SSCBench 用 X 轴伪射线近似（方向错误），evaluator_occ 直接不校正。
- 这就是"深度代理指标（a1_lidar 0.71）涨、3D 指标（IoU）不涨甚至跌"的一个强候选根因：RaySigmaCorrector 在训练（真实射线方向）和评估（X 轴伪射线 / 无校正）之间脱节。

## 问题 3：置信度是否真的有效

**结论：未被实证验证，且归一化存在隐患。**

### 机制与数值

1. 置信度来源：DA3 多视角**几何一致性**（绝对量），实际范围 `[1.0, ~10+]`；保存时 `conf_scale=10000`，uint16 上限 → **clip 到 6.5535**，约 1/3 高置信像素被截断：
   - `docs/DA3深度置信度分析与采样设计.md:76-84`
2. 加载：`conf/10000`，clip `[0, 6.5535]`：
   - `datasets/kitti_360/kitti_360_dataset.py:843`（`conf = conf_raw/10000.0`）、`:847`（`np.clip(conf, 0.0, 6.5535)`）
3. 归一化：`(conf − 1.0) / 5.5535`，clamp `[0.1, 1.0]`（`conf_epsilon=0.1`）：
   - `models/common/render/nerf.py:164`、`models/bts/model/loss.py:68-69`
   - 这是**固定全局归一化**，硬编码假设 conf ∈ [1.0, 6.5535]；conf=1.0 → 0.1（下限），conf=6.5535 → 1.0（高置信端饱和）

### 用法（两处，阈值都是 0.2）

- 采样 `sample_adaptive`：
  - `effective_absrel = absrel_prior / norm_conf`（高置信 → 窄 σ）
  - `norm_conf < 0.2`（即 conf < 2.11）→ 退化为全局均匀采样
- A5 loss：
  - `ray_valid &= norm_conf >= 0.2` → 低置信射线不监督

### 隐患 / 缺口

- **没有任何实证**说明"DA3 conf 与真实深度误差相关"。验证脚本 `scripts/eval_da3_vs_lidar.py` 是**空的（0 字节）**。
- 离线模式下，原始设计**完全跳过 confidence**（`docs/DA3深度置信度分析与采样设计.md:122-133`，`low_conf_mask = None`）。A5 是第一个把 confidence 用作训练阈值的路径，但阈值 0.2、归一化分母 5.5535 都是未经验证的拍脑袋值。
- 归一化非 per-image 自适应（doc 方案 1 建议的是 per-image min/max），且高置信端 1/3 像素饱和在 1.0，失去区分度。

**用户建议的验证（正确）：** 在有 LiDAR 的验证帧上画 (a) DA3 conf—真实深度误差曲线、(b) 分距离段误差、(c) 前视/侧视误差。LiDAR 只用于诊断，不进训练，不破坏自监督设定。

## 优先级建议（如何修改）

1. **问题 1（最高优先级，疑似根因）**：修深度坐标不匹配。
   - 把 DA3 Z 深度转成光线距离：`t = d / v_z`（需把每条射线单位方向的 z 分量传进 `sample_adaptive` 和 `occlusion_supervision_loss`）；或统一用 Z 坐标比较（`z_samps × v_z` vs `d*`）。
   - 这是 seg_acc_side 差、abs_rel_lidar 恶化、3D 过补全的共同根因候选。

2. **问题 2**：修 RaySigmaCorrector 的 train/eval 不一致。
   - 让 eval 一致地应用校正（沿真实射线方向分组，而非 X 轴伪射线），或明确在 eval 时禁用校正并保证训练同步禁用。否则深度代理指标与 3D 指标必然脱节。

3. **问题 3**：先用 LiDAR 验证帧实证 conf—误差相关性，再决定 0.2 阈值与 5.5535 归一化是否成立。若无关，A5 的 conf 掩码 + 采样的 conf 调制都在引入噪声。

4. **问题 4**：等 SSCBench 跑完读最终三档 IoU@12.8/25.6/51.2 + mIoU，对照基线 59.22/44.78/40.40/16.65。早段 Rec>>Prec 已支持"终止 A5"的判断。
