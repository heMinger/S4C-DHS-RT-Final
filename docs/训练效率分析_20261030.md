# 训练效率分析（s4c_dhs_rt_e1 / run3）

分析对象：`out/s4c_dhs_rt_e1/s4c_dhs_rt_e1_backend-None-1_20261029-225544/`（run3，从 run2 的 53550 步续训，当前 ~69350 步）。
数据来源：直接手解 tfevents 二进制（tensorboard 未安装），提取 step 时间戳与 `timing-*` 标量。

## 1. 结论（一句话）

**训练严重受数据加载（CPU 侧）瓶颈，GPU 实际利用率只有 ~17%。** 单步墙钟 ~5.0s，其中 GPU 前向+反向仅 ~0.85s，其余 ~4.2s 在等 DataLoader 出数据（`__getitem__` 单样本 ~5.14s）。

## 2. 实测吞吐

| 指标 | 数值 |
|---|---|
| 墙钟吞吐（原始） | 655 steps/h（5.49 s/step） |
| 墙钟吞吐（剔除 >300s 停顿） | 719 steps/h（5.01 s/step） |
| >300s 停顿次数 / 总耗时 | 25 次 / 3.9 h（≈16% 墙钟） |
| 停顿来源 | `validate_every=5000` 的验证 + checkpoint 保存 |

## 3. 时间去向（run3，`timing-*` 标量，n=317）

| 阶段 | mean (s) | median (s) | 说明 |
|---|---|---|---|
| `t__get_item__` | **5.138** | **5.244** | DataLoader 单样本加载+预处理（瓶颈） |
| `t_forward` | 0.398 | 0.385 | 模型前向 |
| `t_backward` | 0.447 | 0.435 | loss+反向+梯度裁剪+优化器步（accum=2 时每 2 步一次） |
| `t_to_gpu` | 0.0007 | 0.0003 | 可忽略 |
| GPU 合计 | ≈0.85 | ≈0.82 | 前向+反向 |
| `get_batch_secs` | 2.71 | 0.0007 | 双峰：多数即时，少数长阻塞 |

- **GPU 利用率 ≈ 0.845 / 5.01 ≈ 17%。**
- `get_batch_secs` 中位数≈0、均值 2.71s，说明主进程多数时候能从 prefetch 队列即时取数，但周期性阻塞等 worker；`secs_per_iter` 中位数 0.83s、均值 20.18s 的极端双峰也印证这一点（多数步 ~0.83s 纯 GPU，夹杂验证/取数长停顿）。

## 4. 根因：`__getitem__` 为什么 5.14s

每个样本（`frame_count=2` + stereo + fisheye）在 `__getitem__` 里做：

- `load_images`：约 **8 张**图像（左右透视 × 2 帧 + 左右鱼眼 × 2 帧），`cv2.imread` + `cvtColor`；
- `process_img`：8 张 resize + transpose + 转 tensor（含 color aug）；
- `load_depth`：约 **8 张** DA3 深度 uint16 PNG + conf PNG（`cv2.imread` + resize）；
- `load_segmentation_images`：约 **8 张** mask2former 分割 PNG；
- `load_lidar_depth`：1 帧 velodyne `.bin` + 全点云 numpy 投影（含 `Counter` 去重 Python 循环）。

合计每个样本约 **25+ 次小文件读取 + 多轮 numpy/cv2 处理**。数据在 `/mnt/disk1`（疑似机械盘/网络盘），小文件 I/O 密集。

关键点：`_loading_time`（读图）与 `_processing_time`（处理）在代码里**已经计时但未记录**，只记录总 `_proc_time`，所以 I/O vs 计算尚未分开。

## 5. 全量训练时长估计

- 训练集 96901 样本，batch 8（accum 2），drop_last → **~12112 iters/epoch**；
- 60 epoch ≈ **726,720 iters**；
- 按 5.01 s/step → **~1011 h ≈ 42 天**（含验证停顿 ~46 天）。

## 6. 优化建议（按性价比排序）

1. **暴露 `__getitem__` 内部计时**（改动极小）：把 `_loading_time`/`_processing_time` 并入 `timings_dict`，确认是 I/O 还是 numpy/cv2 计算占大头，再对症下药。
2. **提 worker / 常驻**：`num_workers` 8→16/24，`persistent_workers=True`，`prefetch_factor` 2→4~8（前提：训练机 CPU 核数够，先 `nproc` 确认）。若瓶颈是 CPU 计算而非磁盘，此法直接放大吞吐。
3. **缓存确定性预处理**：`load_lidar_depth` 的投影每 epoch 重算且结果固定 → 预计算成 `.npy`/`.png` 一次性缓存；DA3 深度 conf 的 `resize` 也可预存到 192×640 的 float32 文件，省掉每步 resize。
4. **数据本地化**：若 `/mnt/disk1` 是慢盘，把 192×640 预处理数据搬到本地 NVMe 或加 RAM 缓存（如 `mmap`/内存驻留）。
5. **削减验证开销**：`validate_every=5000` 带来 25 次 >300s 停顿（≈16% 墙钟）。可增大间隔、或把验证移出训练主循环异步跑，或降低验证样本数。
6. **AMP**（次要）：当前 `with_amp=false`。数据瓶颈解决后，开 AMP 可再压 GPU 侧的 0.85s，但当前不是主要矛盾。
