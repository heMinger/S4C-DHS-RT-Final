## 4.1 性能剖析（为什么训练这么慢）— 关键发现

从 tfevents 的 `timing-train/*` 分解指标（step > 20000，非评估/非 checkpoint iter 的均值）：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| `t_forward`（GPU 前向） | 0.36 s | ~5% |
| `t_backward`（GPU 反向） | 0.37 s | ~5% |
| `t_to_gpu`（CPU→GPU 拷贝） | 0.002 s | ~0% |
| `secs_per_iter`（纯 train_step） | **0.81 s** | ~12% |
| `get_batch_secs`（等 DataLoader 返回） | **5.72 s** | ~85% |
| `t__get_item__`（单个样本 `__getitem__`） | **7.12 s** | — |

**结论：GPU 实际计算仅 ~0.8 s/iter，但每个 batch 要等数据 ~5.7 s，GPU 利用率约 12%。**
训练慢的元凶是 **DataLoader 数据加载/预处理**，不是模型计算。

`__getitem__` 慢的根因（`datasets/kitti_360/kitti_360_dataset.py` L929 起）：
- `frame_count=2`（`n_frames_render=2`），每个样本要 `cv2.imread` 解码多张 PNG：perspective 2 张 + fisheye 2 张，跨 2 帧 = 8 张图像。
- `return_depth=True`（训练）+ `return_lidar_depth=True`：每帧再加载 DA3 离线深度 PNG + 置信图（多 camera）。
- 每样本还要加载语义分割 mask。
- 全部是**在线 PNG 解码 + CPU 预处理**，无缓存、无 `persistent_workers`、无 `pin_memory`。

**低成本加速建议（按性价比排序）**：
1. 预处理缓存：把 resize 后的图像、DA3 深度、seg mask 一次性存为 `.npy`/memmap，训练时直接 `np.load`（预计 `__getitem__` 7s → <1s，吞吐可提升 3–5 倍）。
2. `persistent_workers=True` + `pin_memory=True`（改动一行，避免每 epoch 重建 worker 进程）。
3. 提高 `num_workers`（8 → 16/24，需确认 CPU 核数与内存）。
4. 若磁盘 IO 是瓶颈（数据在 `/mnt/disk1` 慢盘），把常用数据挪到 SSD 或 tmpfs。

## 4.2 ⚠️ 一个 tensorboard 记录 bug：验证 step 双重计数

`utils/base_trainer.py` L197 的验证全局步长变换：

```python
eval_gst_ep_iters = lambda engine, event_name: (
    ((trainer.state.epoch - 1) * trainer.state.epoch_length + trainer.state.iteration) // config["validate_every"]
)
```

但 ignite 的 `trainer.state.iteration` **本身就是全局累计迭代（跨 epoch 不重置）**，
公式又额外加了 `(epoch-1) * epoch_length`，导致 epoch 偏移被**重复累加**。

后果：tensorboard 里 `metrics-val/*` 的 x 轴 step 在每个 epoch 边界跳变（1–12 → 25–36 → 49–60），
**并非丢掉了 Epoch 2/4 的评估**，而是 step 被错标。正确映射为：

| 训练 epoch | tfevents val step（实际显示） |
|---|---|
| Epoch 1 | 1–12 |
| Epoch 2 | 25–36 |
| Epoch 3 | 49–60 |

（用户终端日志里的 "Epoch 1/2/3" 标签本身是正确的；仅 tensorboard 曲线 x 轴有误，不影响训练。）

### 6.3 核心发现

1. **RT 单独叠加在 S4C 上几乎没有收益**：最好结果 ckpt_5500 的 12.8m IoU=27.45，仅比 S4C 基线(+0.50)，
   远低于 DHS+RT(28.85)。DHS+RT 相对 S4C 的 IoU +1.90 增益在去掉 DHS 后基本消失。

2. **语义 mIoU 严重退化且持续走低**：S4C+RT 最好 mIoU=10.38，低于 S4C 基线(13.77)，远低于 DHS+RT(16.12)；
   且随训练 5500→28500，mIoU 从 10.38 → 9.25 单调下降。说明 RT 的语义增益（DHS+RT mIoU +2.35）依赖 DHS 的采样结构，单独 RT 反而损害语义。

3. **Recall 整体偏低并持续下降**：12.8m Recall 从 49.75(5500) → 45.41(28500)，均低于 S4C(51.85)、DHS+RT(57.66)。
   训练过程中模型在「丢失」近距离占据（欠补全），而非过度补全。

4. **远距离 Recall 波动大**：5500→8000 时 25.6m/51.2m Recall 骤降(-7.06/-7.75)，28500 又回升到 50.15/53.24，
   呈现「先塌后回」的震荡，说明远距离占据预测不稳定（lindisp + z_far 80 + 64 粗采样在远距离样本稀疏）。

## 7. 待外部模型分析的核心问题

1. **RT 的收益是否本质上依赖 DHS？** 数据强烈暗示 DHS（自适应采样）+ RT 是协同的：单独 RT 在固定采样下无法复现 DHS+RT 的 IoU/Recall/mIoU 增益。请从模型结构（`models/bts/model/models_bts.py` 的 RaySigmaCorrector，其 forward 在 411–416 行只读取 39 维坐标编码、丢弃图像特征）角度判断这是否结构必然。

2. **mIoU 随训练单调退化是否正常？** 语义分割在 warm start 后反而变差，是否因为：(a) 深度损失(l1+ssim) 主导梯度、分割损失权重 0.02 太弱；(b) `lambda_density_entropy=0` 无密度约束导致占据分布漂移；(c) RT 的坐标编码注入扰乱了 backbone 的语义特征。

3. **训练设计是否合理？** 从已收敛的 S4C(176000) 权重 warm start，再训练 60 epoch 是否过度？scheduler `step_size=120000`（≈10 epoch）是否太晚衰减，导致前期震荡、后期无法精细收敛。

4. **是否应提前停止？** 当前 mIoU/Recall 趋势 + 60 天满训成本（§4），是否有足够证据在 iter 30000 左右终止，或需要修改配置（启用 `lambda_density_entropy`~0.001、提高 `n_coarse` 到 96、调大 `lambda_segmentation`）后重训。

5. **重训前是否应先解决数据加载瓶颈？** §4.1 显示 GPU 利用率仅 ~12%（`__getitem__` 7.1s vs `train_step` 0.8s）。任何重训前，预处理缓存/`persistent_workers` 等低成本改动可将吞吐提升 3–5 倍，直接决定后续实验的可行性与成本。
